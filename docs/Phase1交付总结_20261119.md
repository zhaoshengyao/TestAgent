## 三个关键代码设计决策

### 1. expected_fail 选方案 B（case 内字段），不选 suite 顶层 known_bugs

```yaml
# ✅ 选：case 内字段
- name: "[problem_user] 购物车流程"
  expected_fail: true
  expected_fail_reason: "Checkout 表单有前端 bug，Continue 会清掉 Last Name"
  max_steps: 80
  timeout_s: 900

# ❌ 弃：suite 顶层 known_bugs
known_bugs:
  - case: problem_user
    reason: "..."
```

理由：case 级字段天然跟随 case 移动/复用/修改，不需要维护一个独立列表做 case name 匹配。

### 2. browser_run_code_unsafe 从 LLM 可见 tool 列表隐藏

```python
_HIDDEN_FROM_LLM = {"browser_run_code_unsafe"}
self._tools = [t for t in all_tools if (t.get("function") or {}).get("name") not in _HIDDEN_FROM_LLM]
# bridge.tool_names 完整保留，框架仍可 bridge.call("browser_run_code_unsafe", ...)
```

理由：这个工具能跑原生 Playwright code，绕过 MCP 协议层 + 自愈 + 循环检测。LMM 一旦发现就再也不用 fill_form/type/click 了。保留 bridge 层面的可达性给未来框架级扩展用。

### 3. 循环检测用滑动窗口，不看"相邻一步"

```python
self._loop_window: list[tuple[str, str]] = []  # 最近 8 步 loop 工具指纹
# 新 step 指纹在窗口里已存在 → streak++（不清零！跨工具累加）
# 没出现 → 只进窗口，不清零 streak
```

理由：LLM 的重试序列是多步模式 find→click→type→find→click→type，不是同工具连刷。只看相邻一步的话跨了 click 就清零，硬拒绝永远触发不了。

## 遗留风险 / 已知问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | **expected_fail 的 passed 没自动回写** | error_user 两次全量都 passed 了，但 yaml 里还写 expected_fail:true → 三态显示"通过 5 + 预期失败 2"而不是"通过 6 + 预期失败 1" | 下次跑如果稳定 passed，手动改成 expected_fail:false |
| 2 | **策略重试只在 fill_form 成功后触发** | 如果 fill_form 返回 is_error，现有 HEALABLE_TOOLS 自愈会先尝试；两种自愈（定位 + 补值）是独立通道 | 足够了，不需要更深耦合 |
| 3 | **循环检测 fingerprint 对 find 排除了 target/similarity** | 如果 LLM 换了 target 但 args 其他相同，可能不被检测 | 看真实跑再调，目前够用 |
| 4 | **browser_press_key 的 fingerprint 只看 key 值** | `Ctrl+A` 和 `Ctrl+A` 当然相同，但如果 LLM 先按 Ctrl+A 再按 Ctrl+A 就是重复 | 已在 problem_user 第四次跑被正确检测 |
| 5 | **eval_streak 硬拒绝在 agent 层触发，run_case() 不识别** | 硬拒绝后 run_instruction 返回"循环终止"文本，run_case 当正常 answer → 走 verify 判定 | 这是正确的！硬拒绝后让裁判根据已有证据判定，比直接 error 好 |
